# Инструкции для агентов и разработчиков

## Назначение

Проект извлекает из русских банковских запросов `PERSON`, `ORG` и `CONTACT_ROLE`.
Ключевая продуктовая цель — **precision**, а не полнота. Фичи приложения намеренно
не входят в NER: они остаются отдельным эмбеддинговым поиском.

## Быстрый старт

```bash
make install
make check
make notebook
```

Для обучения GLiNER2 потребуется `make install-training`. Не менять библиотеку или
чекпойнт, пока владелец проекта не подтвердит точную формулировку ТЗ: `GLiNER v2.x`
и отдельная библиотека `GLiNER2` имеют разные API.

## Неприкосновенные инварианты

- Реальные запросы, ФИО и внутренние справочники нельзя коммитить. Они должны лежать
  только в игнорируемых `data/raw/`, `data/interim/`, `artifacts/` или `models/`.
- Формат разметки: JSONL, `start` включительно, `end` исключительно, индексация Python
  с нуля. `entity["text"]` обязан в точности совпадать с `text[start:end]`.
- У одного запроса может быть несколько сущностей. Сомнительный случай не следует
  разметить как положительный: он идёт в `data/gold/ambiguous.jsonl`.
- Исторические 0/1-флаги — weak labels, не gold truth.
- Известные знаменитости, блюда и рецепты не являются `PERSON`, даже в запросе о переводе.
- `CONTACT_ROLE` (например, «маме») хранится отдельно; downstream при необходимости
  объединяет его с `PERSON` в сигнал «человек/контакт».

## Перед изменением кода

1. Прочитать `README.md` и сохранить слой ответственности: схема/валидация,
   постобработка, оценка, интеграция с моделью.
2. Добавить или обновить тест для изменённой логики.
3. Выполнить `make check`.
4. Не выдавать качество модели без отдельной вручную проверенной golden-выборки.

## Данные и оценка

Основная метрика — exact-span precision по каждому классу и overall. Дополнительно
считается query-level presence для продуктовой интеграции. Порог выбирается на
валидации, а финальное решение — только на зафиксированном golden test set.
