# Bank NER: точное извлечение сущностей из банковских запросов

Минимальный, воспроизводимый старт для русского NER в банковском приложении.
Проект обучает извлечение `PERSON`, `ORG` и `CONTACT_ROLE`; поиск фичей приложения
намеренно остаётся отдельным эмбеддинговым решением.

> Приоритет — precision. Пропуск сущности допустимее ложного срабатывания.

## Что уже есть

- учебный notebook на синтетических данных: `notebooks/01_gliner2_synthetic_pipeline.ipynb`;
- строгая JSONL-схема и валидатор для gold/LLM-разметки;
- exact-span и query-level метрики;
- contract для LLM-as-a-judge с JSON Schema;
- постобработка и версионируемый список исключений для знаменитостей;
- `uv`, `Makefile`, Ruff и unit-тесты.

## Быстрый старт

Нужен Python 3.12 и установленный [uv](https://docs.astral.sh/uv/).

```bash
make install
make check
make notebook
```

Для загрузки и дообучения модели:

```bash
make install-training
```

Первый запуск модели загрузит веса. В промышленном контуре это должен быть одобренный
внутренний mirror/registry. Точное название библиотеки и checkpoint пока намеренно
собраны в одной ячейке notebook: надо подтвердить, означает ли ТЗ `GLiNER v2.x`
или новую библиотеку `GLiNER2`.


## Контракт разметки

Одна строка JSONL — один запрос:

```json
{"id":"gold-0001","text":"Переведи Антону в Мосэнергосбыт","entities":[{"start":9,"end":15,"label":"PERSON","text":"Антону"},{"start":18,"end":31,"label":"ORG","text":"Мосэнергосбыт"}]}
```

Правила:

1. `start` включителен, `end` исключителен; это нулевые Python-индексы.
2. Размечаются все сущности, а `text` сущности обязан быть точной подстрокой запроса.
3. `PERSON` — имя, фамилия или ФИО; `ORG` — получатель/поставщик услуги;
   `CONTACT_ROLE` — роль контакта: «маме», «папе», «тренеру».
4. Знаменитости, исторические личности, блюда и рецепты не размечаются как `PERSON`.
5. При сомнении не ставьте положительную метку: сохраните пример с причиной в
   `data/gold/ambiguous.jsonl`.

Проверка файла:

```bash
uv run python scripts/validate_dataset.py путь/к/gold.jsonl
```

## План переноса на реальные данные

1. Зафиксировать 500–1 000 вручную проверенных запросов как `gold_test.jsonl`.
   Обязательно стратифицировать по коротким запросам, знаменитостям, блюдам,
   падежам, контактным ролям, опечаткам и организациям.
2. Исторические флаги `fio/org/feature/result` использовать только для отбора
   кандидатов. Это weak supervision, так как в них нет границ и есть ошибки.
3. Локальной LLM дать контракт из `bank_ner.llm_contract` и разметить спаны.
   Низкую уверенность направить на ручную проверку, а не в train.
4. Разделить train/validation по тексту и, по возможности, по каноническому имени
   или организации — чтобы утечки вариантов не завысили оценку.
5. Настроить пороги отдельно по меткам на validation и заморозить их до оценки
   на golden test. Для high-precision запуска добавить блэклист знаменитостей и
   аудит ложных срабатываний.
6. Сохранить `data_version`, модель, пороги, hash списка исключений и метрики рядом
   с артефактом модели. Это основа регулярного переобучения.

## Важные границы первого этапа

- Нормализация организаций не смешана с NER. После извлечения добавляется отдельный
  словарь «вариант написания → канонический ID».
- Один лишь список знаменитостей не даст полного precision: он является временным
  защитным слоем, который дополняется негативными примерами и модельным порогом.
- Не измеряйте качество по данным, которыми обучали модель, или по historical flags.
